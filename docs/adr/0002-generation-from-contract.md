# Серверные артефакты генерируются из контракта, роуты объявляются вручную

Задание требует, чтобы серверные артефакты (типы, проверка запросов, маршруты) генерировались из спецификации, с «составом, зависящим от фреймворка». Первоначальное решение тикета «Потребление контракта» было противоположным — бэк читал `openapi.yaml` как справочный документ и писал всё вручную, — но оно противоречит требованию задания. Ревизия: из `contract/openapi.yaml` генерируются **типы** (`openapi-typescript`, тем же инструментом, что и на фронте) и **схемы проверки запросов** (конвертер OpenAPI → TypeBox: схемы `t.*` в Elysia — это и есть TypeBox, они подставляются в определения роутов как валидация входа и сериализация ответа). **Маршруты Elysia объявляются вручную** и ссылаются на сгенерированные схемы: у Elysia нет кодгена OpenAPI → роуты (его нативный `@elysia/openapi` работает в обратном направлении, код → OpenAPI), поэтому состав генерации ограничен тем, что фреймворк позволяет — ровно оговорка «состав зависит от фреймворка».

## Consequences

- Одна команда генерирует всё сгенерированное **в пакете**: `bun run --filter contract compile` (спецификация), `bun run --filter frontend codegen` (типы фронтенда), команда бекенда — тикет #26; CI перегенерирует и падает на ручных правках (`git diff --exit-code`).
- Роуты — единственная ручная часть: их рассинхрон с контрактом ловится типами и тестами по `SPEC.md` (стратегия из issue #17), а не генерацией.
- Решение зафиксировано вместо старого варианта «справочный документ»; тикеты реализации — #18 (фронт) и #26 (бэк).
